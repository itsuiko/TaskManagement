# TaskManagement の品質チェック

第15回に実装全体へ品質チェックを掛け、指摘 A〜G に対応した（Issue #34）。そのとき使った観点を、
次からも同じ形で掛けられるように残したもの。**各観点に「実際に見つかった例」を付けてある。**
観点だけだと抽象的で読み流すが、このリポジトリで本当に起きた例があると探す場所が分かる。

## いつ掛けるか

**機能を1つ実装し終えて、PR を作る前。** 第15回は CRUD が全部揃ってからまとめて掛けたが、
それは理想の形ではない。まとめて掛けると、指摘が溜まって1本の PR が大きくなる。

## 進め方

1. **機械の検査を先に走らせる**（下の「1. 機械の検査」）。機械が見つけられるものを人が探さない
2. **観点 2〜7 を順に見る。** 見るのは今回の変更だけでなく、**その変更で嘘になった既存の記述**も含む
3. **指摘を一覧にして開発者に返す。** 直す前に返す。どれを直すかは開発者が決める
4. 直したら 1 をもう一度走らせる

### 指摘の返し方

| 項目 | 書くこと |
|---|---|
| 種類 | 要件違反 / 誤り / 重複 / 文書のズレ … |
| 指摘 | 何が起きるかを1文で。**利用者か開発者に起きること**として書く |
| 根拠 | ファイルと行。要件違反なら `docs/` の該当箇所も |
| 確かさ | **ファイルを読んで確かめた事実か、仕様からの推測か**を分ける |

**見送りを勧めるものも理由を付けて並べる。** 黙って省くと、検討して外したのか見落としたのかが
あとから区別できない。

## 1. 機械の検査

```powershell
docker compose up -d --wait        # テストが DB を要求する
cd backend;  ./gradlew check       # Checkstyle + テスト
cd frontend; npm run lint          # oxlint
cd frontend; npm run build         # tsc による型の検査
```

**3つとも通ることを確かめてから、通ったと報告する。** 出力を見ずに「通るはず」と書かない。

- Docker Desktop が落ちていると `gradlew check` は全テストが失敗する（接続できないため）。
  コードの問題ではない。起動は開発者に頼む（`.claude/skills/run-app/SKILL.md`）
- `oxlint` は違反が無いとき何も出力しない。終了コード 0 が「違反なし」

## 2. 完了条件を実装が満たしているか

**`docs/requirements.md` 7章の完了条件を、上から1つずつ実装に当てる。** 「たぶん満たしている」ではなく、
その条件を成り立たせている（または壊している）コードの行を特定する。

> **実際に見つかった例（A）**：完了条件 #12「バックエンドを再起動してから開く → タスクがすべて残っている」。
> `data.sql` の先頭に `DELETE FROM tasks` があり、起動のたびに登録したタスクが全部消えていた。
> **「起動すると6件に戻る」という注意書きを設計書・Skill・コードのコメントに書いていたのに、
> 要件違反だとは気づいていなかった。**

**注意書きが増えている場所を疑う。** 「〜すると消えるので先に退避する」のような運用の注意は、
直すべき不具合を言葉で覆っていることがある。

## 3. 文書と実装が食い違っていないか

**機能を足した PR は、その機能を「未実装」と書いている文書を全部直したか。**

Grep で `未実装|まだ無い|だけ。|現在は` を `*.md` に掛け、1件ずつ今も正しいか確かめる。
見る文書：`README.md` / `frontend/README.md` / `CLAUDE.md` / `docs/` の6文書 / `.claude/skills/`。

> **実際に見つかった例（G）**：`frontend/README.md` が第11回のまま「表示だけ。作成・編集・削除は未実装。
> バックエンドは読み取りしか持たない」。`CLAUDE.md` の構成表も「編集・削除・D&D は未実装」。
> `docs/data-design.md` は第12回に解決した問題を「対処が必要」と書いたまま。
> `docs/api-design.md` は冒頭の版が 1.3 で、改訂履歴は 1.4 まであった。

**食い違いを見つけたら、どちらが正しいかを決めてから直す。** 文書を実装に合わせるのが基本だが、
**要件の方が正しい場合は実装を直す**（上の A がそれ）。機械的に文書の側を書き換えない。

## 4. コメントは事実か

**コードは検査できるが、コメントは誰も検査しない。** 特に「〜のために付けている」「〜を防ぐ」と
理由を述べているコメントは、その仕組みが本当にそれを保証するかを確かめる。

> **実際に見つかった例（D）**：`TaskService.create` に「間に別の登録が割り込むと同じ番号が付くので、
> @Transactional を付けている」とあった。`@Transactional` が保証するのは「途中で失敗したら全部取り消す」
> ことで、**割り込みは防がない**（PostgreSQL の既定の分離レベル READ COMMITTED では防げない）。
> 同じ誤りを「create と同じ理由」と参照するコメントが、あと2か所にあった。

**「同じ理由」「上と同じ」と書いてあるコメントは、参照先が誤っていると一緒に誤る。**

## 5. 同じ判断が複数の場所に書かれていないか

行数が同じかどうかではなく、**同じ判断かどうか**で見る。同じ判断が複数箇所にあると、
変えるときに1か所だけ直し忘れる。

> **実際に見つかった例（F）**：`frontend/src/api.ts` の5つの関数すべてに、「fetch を try で囲む →
> `response.ok` を見る → 文言を組み立てる」の十数行が書いてあった。内部関数 `request` にまとめた。

**逆に、形が同じでも意味が違うものはまとめない。** `TaskCreateInput` と `TaskUpdateInput` は
項目が同じだが別の型のまま（`frontend/src/types.ts` に理由がある）。

現在も残っている重複：`"todo|doing|done"` と `"high|medium|low"` の正規表現が、バックエンドの
3つの record に書いてある。値を増やすときは3か所とも直す。

## 6. アクセシビリティ

非機能要件（`docs/requirements.md` 6章）：**キーボードだけで作成・編集・削除ができる／入力欄に
ラベルがある／コントラスト比 4.5:1 以上。**

- 押せる要素は `<button>` か、`role="button"` + `tabIndex={0}` + Enter と Space の処理の3点セット
- `<label htmlFor>` と入力欄の `id` が対になっている
- **`role` を付けるとき、元の要素の意味を消していないか**

> **実際に見つかった例（E）**：カードが `<li role="button">` だった。`<li>` の「リストの項目」という意味が
> 「ボタン」で上書きされ、`<ul>` の直下に項目が1つも無い扱いになる。`<li>` は素のまま残し、
> 中の `<div>` に `role="button"` を移した。

## 7. 失敗が隠されていないか

**AI は、エラーが出なくなる方向へ直そうとする。**（第15回の講義で講師が挙げた点）
エラーが出ないことと、問題が無いことは別である。次のものが増えていないかを見る。

| 見るもの | なぜ問題か |
|---|---|
| 空の `catch`、`catch` して何もせず続行 | 失敗したのに成功したように見える |
| `// oxlint-disable`、`@SuppressWarnings`、`@ts-ignore`、`as any` | 検査を黙らせただけで、指摘された問題は残っている |
| `@Disabled`、テストの削除、期待値を実際の値に合わせて書き換え | 落ちるテストを通るように「直した」 |
| `checkstyle.xml` や `.oxlintrc.json` から規則を外す | 上と同じ |
| 別のポートで起動する、`TaskStop` の「止まった」を信じる | 動いているように見えるだけ（`CLAUDE.md`） |
| `response.ok` を見ずに `response.json()` を呼ぶ | `fetch` は 404 でも 500 でも例外を投げない |

このアプリの要件にも同じ考え方がある——F-07「保存に失敗した場合は、画面上にエラーを表示する
（**成功したように見せてはならない**）」。

**現時点（Issue #34）で、上の表の書き方は main に1つも無い。** 増えたら、その PR で入ったもの。

**検査に引っかかったときの決着は2つだけ：コードを直すか、その規則を採らないと決めて理由を書くか。**
黙らせる指定で通さない。
