## 1. 採用する構成

版1.0から版3.0まで「未定」として保留していた。要件定義（何を作るか）が固まったため、ここで確定する。

| 層 | 採用するもの | バージョン |
|---|---|---|
| フロントエンド | React + TypeScript | **React 19.3.0 / TypeScript 6.0.3** |
| フロントエンドのビルドツール | Vite | **8.2.2** |
| CSS | Tailwind CSS | **4.3.3** |
| フロントエンドの実行環境 | Node.js（LTS） | **24.19.0** / npm **11.17.0** |
| バックエンド言語 | Java | **25**（LTS。Temurin 25.0.4.1） |
| バックエンドのフレームワーク | Spring Boot | **4.1.1** |
| バックエンドのビルドツール | Gradle（Groovy DSL） | **9.7.1**（Wrapper が取得） |
| データベース | PostgreSQL | **18**（イメージ `postgres:18` の実体は 18.6） |
| データベースの実行環境 | Docker（Docker Desktop / WSL 2 backend） | Engine **29.7.2** / Compose **5.5.0** |

**上の数字はすべて実物のコマンドで確認したもの**（`java -version` / `gradlew --version` / `node -v` / `docker version` / `postgres --version` / `package-lock.json`）。

### `package.json` に書いてある数字と、実際に動いている数字は違う

`package.json` の指定は**範囲**であって、固定した値ではない。

| | `package.json` の指定 | 実際に入っている |
|---|---|---|
| React | `^19.2.8` | **19.3.0** |
| TypeScript | `~6.0.2` | **6.0.3** |

先頭の記号が許す範囲を表す。`^19.2.8` は「19 系ならマイナー更新まで許す」、`~6.0.2` は「6.0 系のマイクロ更新まで許す」。

バージョンは左から**メジャー・マイナー・マイクロ**で、

- **マイクロ**（19.2.8 → 19.2.9）はセキュリティ修正や細かい訂正
- **マイナー**（19.2 → 19.3）は機能追加を含むことがあるが、動いているものを壊さない範囲に留める約束
- **メジャー**（19 → 20）は壊れる変更を含みうる

**この表には実際に動いている方を書いている。** `package.json` を読んで「19.2.8 が動いている」と考えると、不具合を追うときに実物とずれる。正確な値は `package-lock.json` にある。

**対象外とするもの**

- **Next.js** — React をベースにした上位のフレームワーク。実務では標準に近いが、本アプリの規模では React 単体で足りるため今回は使わない
- **認証・ログイン機構** — 利用者が本人1名のため（[要件定義書 3章](./requirements.md)）

版4.1まで、フロントエンドのバージョンは「着手時に決定」として空欄にしていた。**その時点での安定版の最新を選ぶ**という方針だけを先に決めてあり、版5.0で実際の数字を入れた。選定の理由は8章。

## 2. 満たすべき条件と、その満たし方

版2.0でデータベースを採用した時点で、選定の条件は4つに具体化していた。採用構成がそれぞれをどう満たすかを対応させる。

| 条件 | 満たし方 |
|---|---|
| フロントエンド / バックエンド / データベースの3層構成を取れること | React（ブラウザ）→ Spring Boot（API）→ PostgreSQL。[データ設計書 1章](./data-design.md) の構成図と一致する |
| ブラウザから呼び出せる Web API を提供できること | Spring Boot の Web 機能（`spring-boot-starter-webmvc`）で REST API を提供する |
| ドラッグ＆ドロップを無理なく実装できること | React にはドラッグ＆ドロップ用のライブラリが複数あり、選択肢が確保できる |
| 学習目的として、内容を追いやすい構成であること | 下記 3章 |

**条件が先にあって、選定が後**という順序は崩していない。

## 3. なぜ Java + Spring Boot なのか

AI を使って開発する前提であれば、フロントエンドと同じ **TypeScript** でバックエンドまで書く（Node.js）方が、言語が1つで済み効率が良い。実務ではその選択が増えている。それでも Java を採る理由は2つ。

**理由1：学習しやすさ**

Java は入門者向けの書籍・記事・資格が圧倒的に多い。AI に聞いて理解するだけでなく、**裏で何が起きているかを本で確かめられる**。TypeScript は中級者向けの資料に寄っており、この段階では学びにくい。

**理由2：AI を前提としない現場が残ること**

「AI が使えれば可」とはしない採用基準の現場は今も多い。求人で TypeScript が条件に出るのは基本フロントエンドで、**バックエンドの TypeScript 求人はほとんど存在しない**。一方で Java + Spring Boot は汎用性が高く評価されやすい。

**言語そのものへのこだわりは、現在ほぼ無い。** Java でも TypeScript でも Ruby でも Python でも成立する。ただしフレームワークの選定は開発効率に直結するため、そちらは意味を持つ。

## 4. なぜ Spring Boot 3系ではなく 4.1.1 なのか

講義（2026年3月収録）は「Java 25 ＋ Spring Boot 3系の最新」を指定している。本プロジェクトはこれを 4.1.1 に変更した。**判断の原則は変えておらず、原則を今日の日付に適用した結果として数字が動いた。**

**原則：新規プロジェクトであえて古い版を選ぶ理由はない。サポートが切れた版はセキュリティ上の問題が見つかっても修正されない。**

2026-09-05 時点の事実：

- **Spring Boot 3系はすべてOSSサポートが終了している。** 最後まで残った 3.5 系が 2026-06-30 に EOL（End of Life）を迎え、以降は無償のセキュリティ修正が出ない
- **公式の雛形配布サイト Spring Initializr が 3系を配布していない。** 選択できるのは 4.0.8 と 4.1.1 のみで、既定は 4.1.1

つまり 3系は「選ばない」のではなく「選べない」。

**Java 25 との組み合わせ**：Spring Boot 4.1 は Java 17〜26 に対応しており問題ない。ビルドツールの Gradle も 9.1.0 以降が Java 25 に対応しており、Spring Initializr が対応版の Wrapper を同梱する。

**Java 25 を選んだ理由**：Java は半年ごとに新版が出るが、数年に1度だけ長期サポート対象の **LTS**（Long Term Support）が出る。LTS は 8 / 11 / 17 / 21 / 25 で、25 が最新（2025年9月リリース）。新規に作るものが今後さらに古くなっていくことを考えると、**開始時点で最も新しい LTS を選ぶ**のが合理的。

**トレードオフ（承知の上で選択している）**：Java 25 と Spring Boot 4系は新しいぶん、書籍・記事・AI の学習データが薄い。詰まったときに答えが見つかりにくくなる可能性がある。それでもサポート期間を優先した。

## 5. なぜ PostgreSQL 17 ではなく 18 なのか

講義は PostgreSQL **17** を指定している。本プロジェクトは **18** にした。4章と同じ原則（新規はサポート中の安定版最新）を適用した結果である。

**ただし4章とは状況が決定的に違う。**

| | Spring Boot 3系（4章） | PostgreSQL 17（この章） |
|---|---|---|
| サポート状況 | 2026-06-30 に全て終了 | EOL は 2029-11。**まだ現役** |
| 公式配布 | Spring Initializr が配布を停止 | 配布されている |
| 判断 | **選べなかった** | **選べたが、選ばなかった** |

17 を選んでも実害はなかった。それでも 18 にしたのは、このアプリが今後さらに古くなっていくことを前提に、**開始時点で最新を取っておく方が、後からの移行回数が減る**と判断したため。

**トレードオフは実際に発生した（承知の上で選択している）**：講義どおりに `/var/lib/postgresql/data` をマウントしたところ、コンテナが終了コード1で起動に失敗した。PostgreSQL 18 以降の公式イメージは、データをメジャーバージョン別のディレクトリ（`18/docker`）に置く方式に変わり、**マウント先は `/var/lib/postgresql`（`/data` を付けない）1つに変更されている**。17 を選んでいれば踏まなかったエラーで、これが「最新を選ぶ」ことの代償にあたる。

## 6. データベース周りで決めたこと

### テーブルの作り方：`spring.jpa.hibernate.ddl-auto=update`

エンティティの定義に合わせて Hibernate がテーブルを作り、足りない列を足す。**この設定は本番環境では使わない。**

理由は、**`update` が「追加」しかしないため**。列名の変更・列の削除・型の変更を検知せず、古い列がそのまま残る。開発中は「起動すれば揃っている」利便性が勝つが、本番ではデータベースの実際の姿と設計が静かにずれていく。

| 捨てた案 | 捨てた理由 |
|---|---|
| `validate` + Flyway でマイグレーション管理（現場の標準） | 変更履歴をファイルで管理でき正確だが、道具が1つ増える。接続確認が目的の段階では重い |
| `create-drop` | 起動のたびにテーブルごとデータが消える。動作確認に使えない |

### データベースのパスワードを `compose.yaml` に平文で書いていること

**これは判断の結果であって、見落としではない。**

- このデータベースは `127.0.0.1:5432` にしか公開しておらず、外部から届かない
- 利用者は本人1名で、守るべき他人のデータが存在しない
- clone した人がそのまま `docker compose up` で起動できることが、Docker を使う利点そのもの

**外部に公開する段階になったら、この判断は無効になる。** その時点で環境変数か `.env`（Git の管理対象外）に移す。

### テストが Docker に依存するようになったこと

JPA を入れたことで、`contextLoads` テストがデータベース接続を要求するようになった。**`docker compose up -d` を先に実行していないと `gradlew test` が失敗する。**

Testcontainers（テスト用にコンテナを自動起動する仕組み）や H2（メモリ上の簡易データベース）を使えば依存を外せるが、どちらも道具が1つ増える。今回は「**テストの前にコンテナを起動する**」という運用ルールで対応する。

## 8. フロントエンド側で決めたこと

### なぜ Node.js は最新（26.7.0）ではなく LTS（24.19.0）なのか

**4章（Java 25）と同じ「最新の LTS を取る」基準を適用した。** Node.js は偶数版だけが LTS になり、**リリースの半年後に切り替わる**。2026-09 時点で 26 はまだ「Current」で、LTS は 24 である。

| | 選べたか | 判断 |
|---|---|---|
| Spring Boot 3系（4章） | **選べなかった**（配布停止） | ― |
| PostgreSQL 17（5章） | 選べた | **選ばなかった**（最新の18を取った） |
| Node.js 26（この章） | 選べた | **選ばなかった**（LTSの24を取った） |

**5章と逆の結論になっているのは、基準が違うからではなく、対象の性質が違うため。** PostgreSQL に LTS という区分は存在せず「最新の安定版」が最新版そのものだが、Node.js には LTS が明示的に存在し、**Current は「安定版の最新」ではない**。同じ「サポート中の安定版最新を取る」原則を当てはめた結果として、片方は最新、片方は1つ前になった。

### モノレポ構成（`backend/` と `frontend/` を同じリポジトリに置く）

バックエンドとフロントエンドは**互いに依存しない**（疎結合）。フロントは決められた形でリクエストを送るだけで、バックエンドは相手が何であっても応答する。この性質から、従来はリポジトリを分けることが多かった。

**それでも1つにまとめたのは、依存関係と作業単位が別の話だから。** 1つの機能を作るときはバックエンドとフロントを同時に触る。分けると「読み取り API が完成しているか」を判断する材料が手元から消え、毎回もう一方の情報を運んでくる手間が発生する。

**トレードオフ**：同じリポジトリで作業するため、フロントとバックエンドの変更が同じファイルに当たって競合する可能性がある。開発者が1名の本プロジェクトでは発生しない。

### CORS はバックエンドではなく Vite で解決する

ブラウザは 5173、バックエンドは 8080 で動く。**ポートが違うとブラウザは「別のオリジン」とみなし、通信を遮断する**（CORS）。

| 案 | 採否 |
|---|---|
| **Vite の `server.proxy` で `/api` を 8080 へ中継する** | **採用。** ブラウザからは同一オリジンへの要求に見える |
| バックエンドに `@CrossOrigin` を書いて 5173 からの要求を許可する | 却下 |

却下したのは、**非機能要件「API は同一オリジンからのリクエストのみ受け付ける」（[要件定義書 6章](./requirements.md#6-非機能要件)）に反する**ため。開発の都合でバックエンド側の受け入れ範囲を広げると、その設定は本番にもついて回る。

### Tailwind CSS は4系で、3系と設定方法が違う

**3系までの `tailwind.config.js` と `@tailwind base;` などのディレクティブは使わない。** 4系では設定を Vite プラグイン（`@tailwindcss/vite`）が担い、CSS 側は `@import "tailwindcss";` の1行になる。

記事や書籍、AI の回答の多くはまだ3系の手順を書いている。**「設定ファイルが無い」ことは不備ではない。**
